# Raft: конфигурация, состав кластера и метрики

`zhttpd-raft` — отдельный модуль/процесс на каждый инстанс zhttpd. Он использует
[HashiCorp Raft](https://github.com/hashicorp/raft) для выборов лидера,
RequestVote/AppendEntries, большинства, смены участников и передачи снимков.
Постоянный журнал и term/vote хранятся в
[raft-boltdb/v2](https://github.com/hashicorp/raft-boltdb/tree/master/v2)
с включённым fsync. Версии и контрольные суммы зафиксированы в
`modules/raft/go.mod` и `go.sum`. Модуль поддерживает Linux и macOS.

Raft реплицирует три вида данных:

- Полные конфигурационные документы zhttpd, адресованные конкретному node ID.
  Каждый узел хранит документы всего кластера, но экспортирует только свой.
- Состав голосующих участников через штатные операции Raft AddVoter/RemoveServer.
  Контактные API-адреса новых участников также записываются в журнал.
- Пакеты метрик workers каждого инстанса. Время измерения сохраняется, а не
  заменяется временем доставки или восстановления снимка.

## Путь данных

```text
workers zhttpd → локальный inbox → zhttpd-raft → лидер → большинство дисков
                                                          ↓ commit
workers zhttpd ← локальный view ← применение журнала на каждом участнике
                                      ↓
                        собственный server.toml → auto reload
```

На запросе HTTP нет ожидания консенсуса. Обрабатываются только локальные снимки
подтверждённых метрик, с прежним TTL и защитой от циклов 307. Если большинство
недоступно, новые конфигурации и метрики не подтверждаются. Старые метрики
истекают, и HTTP-сервер продолжает локальную обработку. Raft не реплицирует тела
HTTP-запросов, файлы сайта, состояние upstream-приложений или пользовательские
сессии.

## Сборка и локальный запуск

Нужны Zig из `mise.toml` и Go 1.27.1. Обычный `zig build` остаётся независимым
от Go; companion собирается явно:

```bash
zig build
zig build raft
python3 examples/raft/make-local.py
```

Последняя команда создаёт три конфигурации в `.run/raft-demo`, случайный токен
и печатает шесть команд запуска: три агента и три HTTP-сервера. Запустите их
в отдельных терминалах либо под process supervisor. Для перезапуска используйте
те же файлы и каталоги `data`; генератор намеренно не перезаписывает существующее
состояние. HTTP-порты примера: 9501–9503, API: 9401–9403, Raft: 9301–9303.

Проверка первого агента:

```bash
curl -H "Authorization: Bearer $(cat .run/raft-demo/token)" \
  -H 'X-Zhttpd-Cluster: local-demo' http://127.0.0.1:9401/v1/status
```

Поле `leader` сообщает API-адрес текущего лидера. Запросы изменения и согласованного
чтения следует отправлять ему; follower возвращает 409 с адресом лидера,
без автоматических цепочек HTTP-редиректов.

## Конфигурация агента

Пример для первого узла (аналогичные локальные файлы нужны на остальных):

```json
{
  "id": "node-a",
  "cluster_id": "production-web",
  "raft_address": "10.10.0.1:9301",
  "api_address": "10.10.0.1:9401",
  "data_dir": "/var/lib/zhttpd/raft",
  "metrics_inbox": "/var/run/zhttpd/inbox",
  "metrics_view": "/var/run/zhttpd/view",
  "config_output": "/etc/zhttpd/server.toml",
  "token_file": "/etc/zhttpd/raft-token",
  "peers": [
    {"id":"node-a","raft_address":"10.10.0.1:9301","api_address":"10.10.0.1:9401"},
    {"id":"node-b","raft_address":"10.10.0.2:9301","api_address":"10.10.0.2:9401"},
    {"id":"node-c","raft_address":"10.10.0.3:9301","api_address":"10.10.0.3:9401"}
  ],
  "bootstrap": true,
  "interval_ms": 1000,
  "metrics_ttl_ms": 5000,
  "tls": {
    "ca": "/etc/zhttpd/cluster-ca.crt",
    "certificate": "/etc/zhttpd/node-a.crt",
    "key": "/etc/zhttpd/node-a.key"
  }
}
```

Сертификаты должны быть выпущены доверенным CA кластера, иметь SAN для адресов
подключения и разрешать serverAuth/clientAuth. Raft RPC и API используют TLS 1.3
с проверкой клиентского сертификата. API дополнительно требует общий секрет из
`token_file` (32–256 символов) и `X-Zhttpd-Cluster`. Это доверенный административный
контур: обладатели клиентского сертификата и секрета могут менять конфигурацию
и участников. Файлы документов, журнал и снимки могут содержать секреты конфигурации;
ограничьте доступ к каталогам тем же сервисным UID.

Только для локальной разработки разрешено `"insecure_loopback": true` без `tls`.
Все адреса при этом обязаны быть буквальными loopback IP; wildcard, hostname и
внешние IP отклоняются. Секрет API требуется и в этом режиме. Raft greeting
содержит cluster ID, поэтому узлы разных кластеров не смешивают RPC.

Относительные пути разрешаются от каталога JSON. `data_dir`, `metrics_inbox`
и `metrics_view` должны быть отдельными локальными каталогами; общий filesystem
между машинами больше не нужен. Каталоги создаются с правами 0700. Родитель
`config_output` должен существовать; пустое/отсутствующее `config_output` отключает
локальный экспорт документов, но не их репликацию.

В TOML zhttpd нужны разные каталоги чтения и публикации:

```toml
[load_balancer]
enabled = true
node_id = "node-a"
backend = "/var/run/zhttpd/view"
publish_backend = "/var/run/zhttpd/inbox"
# node_ids, node_urls и лимиты — как в документации балансировщика
```

Без `publish_backend` сохраняется прежний режим общего файлового каталога.
В Raft-режиме `backend` соответствует `metrics_view`, а `publish_backend` —
`metrics_inbox`; писать в `view` должен только companion. Согласуйте `ttl_ms`
zhttpd с `metrics_ttl_ms` агента; часы узлов должны быть синхронизированы.
Период агента: 100–60000 мс; TTL: 3000–300000 мс и минимум три периода.

## Bootstrap, перезапуск и изменение состава

Для нового кластера задайте одинаковый список из трёх или пяти voters на всех
начальных узлах, разные ID/адреса и `bootstrap=true`. Bootstrap выполняется
только при отсутствии уже существующего журнала/снимков. Повторный запуск
восстанавливает прежнюю конфигурацию Raft, не создаёт её заново из `peers`.
Каталог закреплён за парой cluster ID/node ID; чужой каталог отклоняется.

У нового участника задайте `bootstrap=false`, уникальные ID и адреса, пустой
новый `data_dir` и контакты существующего кластера в `peers`. Запустите его,
затем отправьте лидеру:

```text
POST /v1/members
{"id":"node-d","raft_address":"10.10.0.4:9301","api_address":"10.10.0.4:9401"}
```

API добавляет голосующего участника через `AddVoter`. Не считайте ответ гарантией
полного догоняния журнала: новый voter может сразу увеличить требуемый кворум.
Меняйте состав по одному узлу и дождитесь его синхронизации перед следующей операцией. Текущий API
возвращает подтверждение изменения Raft-конфигурации; факт полного догоняния
проверяйте по applied index/status. Новый voter получает журнал или снимок
и ранее записанные документы/метрики. Для удаления отправьте
`DELETE /v1/members/node-d`. Удаление текущего лидера через этот API запрещено:
остановите его, дождитесь нового лидера и удалите прежний через нового лидера.
После удаления остановите companion удалённого участника.

Список `peers` — первоначальные контакты/bootstrap, а не механизм изменения
живого состава. Замена адреса действующего ID отклоняется; используйте удаление
и новый ID. Не удаляйте журнал для «починки» живого участника. Изменение voters
требует действующего большинства; автоматического force-recovery при потере
большинства здесь нет. Максимум — 32 участника.

Raft-voters и HTTP-адреса назначения — разные настройки. Добавив voter,
опубликуйте необходимые документы `server.toml` с обновлёнными `node_ids` и
`node_urls`, чтобы он участвовал также в HTTP-балансировке. Это позволяет
подключить и синхронизировать узел до направления клиентского трафика.

## API документов и метрик

Все вызовы требуют Authorization и cluster header; для TLS также клиентский
сертификат. Тип содержимого — JSON.

| Метод и путь | Результат |
| --- | --- |
| `GET /v1/status` | Локальная диагностика: роль, лидер, applied index, последняя известная membership и ошибка экспорта; не линейризуемый снимок кластера |
| `GET /v1/state` | Согласованное чтение FSM на лидере после VerifyLeader + Barrier |
| `PUT /v1/config` | CAS-обновление полного документа одного узла |
| `POST /v1/metrics` | Подтверждение пакета измерений одного участника; обычно вызывает companion |
| `POST /v1/members` | Добавление voter через Raft |
| `DELETE /v1/members/{id}` | Удаление voter через Raft |
| `POST /v1/snapshot` | Принудительный снимок; обычно снимки делаются автоматически |

Пример тела `PUT /v1/config`:

```json
{
  "node": "node-b",
  "expected_revision": 0,
  "toml": "[server]\ncompatibility='self'\n[http]\nlisten='127.0.0.1:9502'\nresponse='updated'\n"
}
```

Для первой записи используется revision 0; успешный ответ возвращает 1. Следующий
запрос должен указать 1 и получит 2. Неверная revision возвращает 409, не меняя
документ. Максимум одного документа — 64 KiB. В рабочем документе сохраняйте
настройки балансировщика и правильные локальные пути/адреса соответствующего
узла. API сохраняет полный текст, не объединяет TOML-таблицы.

Ответ 200 означает подтверждение журналом большинства, а не успешное применение
HTTP-конфигурации. FSM экспортирует файл атомарно, после чего существующий watcher
zhttpd перезагружает его. Неверная конфигурация сохраняется в Raft, но HTTP-сервер
оставляет прежнюю рабочую конфигурацию и пишет диагностику; исправьте документ
следующей revision. Предварительно используйте `zhttpd -t` на целевом узле.
`export_error` показывает файловые ошибки, не ошибки парсера zhttpd. Внешние
include-файлы, сертификаты и их содержимое отдельно не распространяются.

Ошибка/таймаут после отправки записи может означать неизвестный исход операции:
проверьте состояние у текущего лидера, затем повторяйте с тем же expected_revision.
Отключённый узел не может подтвердить запись меньшинством. Изменения документов
разных узлов — отдельные транзакции; синхронное переключение всех HTTP-workers
в один момент не обещается.

## Долговечность и нагрузка

Метрики отправляются одним пакетом на инстанс за интервал, только когда данные
изменились. Они проходят тот же долговечный журнал, что и конфигурация: это
увеличивает сетевую и дисковую нагрузку относительно прежнего общего каталога.
Начните с периода 1 секунду и выберите TTL с запасом на выборы, fsync и задержки.
До 256 записей workers в пакете; в inbox допускается до 4096 элементов.
Старые файлы умерших workers пропускаются по TTL и могут быть удалены при
обслуживании завершённых процессов.

Снимки проверяются каждые 20–40 секунд при 256 новых записях; остаются три снимка
и 64 trailing log entries. При восстановлении исходное время метрики не меняется.
Экспортный cursor не позволяет более старому снимку откатить уже экспортированный
документ. Export выполняется только из применённых committed entries; Raft WAL
никогда напрямую не используется как источник HTTP-метрик.

## Проверки

```bash
go -C modules/raft test -race ./...
zig build test-raft-e2e
zig build test test-load-balancer-e2e
```

E2E запускает три настоящих Raft-процесса и три HTTP-сервера, затем проверяет
балансировку по committed metrics, CAS и auto reload, snapshots, SIGKILL лидера,
новые записи с оставшимся большинством, запрет записи в меньшинстве, истечение
метрик без кворума, восстановление, ввод/вывод четвёртого участника и полный
перезапуск с диска. Unit-тесты дополнительно проверяют mTLS, отказ без клиентского
сертификата, разделение cluster ID, валидацию метрик и запрет отката экспорта.
