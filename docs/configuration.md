# Конфигурация zhttpd

По умолчанию сервер читает `config.toml`. Пути в нём разрешаются относительно
каталога этого файла; `server.prefix` меняет корень путей для ресурсов и журналов.
`server.config` всегда отсчитывается от каталога TOML. Проверка без запуска:

```sh
mise run build
mise exec -- zig-out/bin/zhttpd -t -c config.toml
mise exec -- zig-out/bin/zhttpd -c config.toml
```

## Выбор совместимости и модулей

```toml
[modules]
http = true
self = true
nginx = true
apache = true
litespeed = true
caddy = true
websocket = true
fastcgi = true
wsgi = true
logging = true
acme = true

[server]
compatibility = "nginx"
config = "nginx.conf"
prefix = "."
pid = "server.pid"
auto_reload = true # по умолчанию
```

`server.compatibility` **обязателен**: `self`, `nginx`, `apache`, `litespeed`
или `caddy`. Неизвестное значение, отсутствующий выбор и выключенный выбранный
адаптер — ошибки. Для внешних форматов обязателен `server.config`; для `self`
он запрещён. Таблицы `http` разрешены только при `self`.

Все перечисленные модули по умолчанию включены. Переключатели управляют
конфигурацией и выполнением, а не исключают код из бинарного файла. Выключение
`http` запрещает запуск HTTP-сервера. WSGI требует также `fastcgi`. Ссылка на
выключенный обработчик — ошибка, в том числе после импорта nginx. Выключение
`logging` отключает журналы запросов и ошибок рабочих процессов; диагностика
запуска и управляющего процесса остаётся на stderr. Явный `[logging]` при
`modules.logging=false` считается ошибкой.

Для старых сценариев `-c nginx.conf` продолжает выбирать nginx без TOML.
`--compatibility apache|litespeed|caddy -c FILE` выбирает другой прямой формат;
переключатели модулей доступны через TOML.

## Автоматический reload

По умолчанию master отслеживает `config.toml`, выбранный `server.config` и
конфигурационные зависимости загрузчика:

| Режим | Отслеживаемые зависимости |
| --- | --- |
| `self` | Нативные настройки в TOML |
| nginx | Основной конфиг и рекурсивные `include`, в том числе glob-шаблоны |
| Apache | Основной конфиг, `Include` и `IncludeOptional`, включая glob-шаблоны |
| OpenLiteSpeed | `httpd_config.conf` и файлы виртуальных хостов из `configFile` |
| Caddy | Caddyfile и рекурсивные `import`, включая glob-шаблоны |

Прямой запуск с `--compatibility ... -c FILE` тоже включает наблюдение.
Поддерживаются те же формы include/glob, что и у соответствующего адаптера;
для OpenLiteSpeed отслеживается его нативный формат.

Содержимое проверяется не чаще одного раза в 250 мс. После обнаружения изменения master ждёт
500 мс без новых изменений, затем выполняет обычный безопасный reload. Обычно
сохранение применяется примерно за секунду; выпуск новых сертификатов ACME
может занять больше времени. PID master остаётся прежним, workers заменяются
плавно. Проверка по содержимому замечает изменения при сохранённых размере и
mtime, атомарную замену файла и смену symlink. Сохранение идентичного содержимого
или `touch` не вызывает reload.

Добавление/удаление файлов, совпадающих с include/import glob, также вызывает
reload, даже если шаблон первоначально не находил файлов. При ошибке остаётся
рабочая конфигурация. Наблюдатель сохраняет зависимости последней попытки,
включая отсутствующие файлы: их создание или исправление конфигурационного
файла автоматически запускает следующую попытку. Одна и та же ошибка без
изменений не повторяется в цикле. После успешного применения удалённые из
конфигурации зависимости перестают отслеживаться.

Сертификаты, приватные ключи, файлы паролей TLS и `dns_env_file` также отслеживаются во всех режимах,
включая прямые нативные конфиги. Статические ресурсы и журналы не отслеживаются.
Правила ротации TLS и credentials описаны ниже.

Для отключения задайте `[server] auto_reload = false`. Это значение применяется
вместе с новой конфигурацией. Пока наблюдение выключено, повторное включение
требует `-s reload` либо SIGHUP. Ручной reload всегда доступен и не ждёт задержку
наблюдателя. Задержка объединяет близкие сохранения, но не делает несколько
файлов одной транзакцией: для согласованных массовых правок можно временно
отключить наблюдение и применить готовый набор ручным reload.

### Сертификаты, ключи и DNS credentials

Наблюдение охватывает ручные пары TLS из нативных конфигов / `[http.tls]`,
файлы всех сертификатов `[[acme.certificates]]` (включая дополнительные SNI-пары),
файлы паролей TLS и env-файл DNS-провайдера каждой записи. Используется тот же `server.auto_reload`,
проверка содержимого и задержка после сохранения. Создание/восстановление,
атомарная замена файла, symlink и изменение его целевого файла поддерживаются.
Переписывание тех же байтов не вызывает повторный reload.

При раздельном сохранении сертификата и ключа новая конфигурация включается
только после успешной загрузки TLS и проверки соответствия приватного ключа
сертификату. Повреждённый PEM, несовпадающая пара или отсутствующий ручной файл
оставляют текущие workers и их TLS-контексты активными. Зашифрованные PEM-ключи
поддерживаются с файлом пароля; неверный пароль или отсутствие источника пароля
отклоняет новую конфигурацию без интерактивного запроса. Исправление файла
автоматически повторяет проверку. Для отсутствующей managed-пары ACME может
выпустить сертификат в фоне, как при обычном reload. Успешное переключение
обновляет новые соединения, включая SNI, HTTP/2 и HTTP/3, без смены PID master.

Изменение `dns_env_file` ставит проверку **соответствующего сертификата** в очередь
сразу после успешного reload; часы ожидания `check_interval_seconds` не нужно
выжидать заново. Другие записи сохраняют свои сроки. Выпуск/продление всё равно
следует `renew_before_days`: изменение credentials не принуждает к перевыпуску
ещё не требующего продления сертификата. Если файл используют несколько записей,
проверяются все эти записи. Значения читаются lego в дочернем процессе; окружение
master не меняется. Наблюдатель не выводит содержимое ключей или env-файлов в журнал.

Отсутствующий или пустой env-файл отклоняет новую конфигурацию, сохраняя HTTPS.
Неподходящие credentials могут быть отклонены самим lego или DNS API; текущие
сертификаты при этом сохраняются. Исправление только env-файла запускает новую
попытку автоматически, в том числе для файла, отсутствовавшего при добавлении
сертификата. Если внешняя причина ошибки устранена без изменения файлов,
повторную попытку можно запросить изменением комментария в конфиге или ручным reload.

Записываемая текущим заданием lego пара временно исключается из проверки файлов.
После завершения дочернего процесса учитывается конечное состояние, и результат
проходит обычную проверку TLS. Это предотвращает reload из-за промежуточных записей
и циклы продления. Если credentials изменились во время задания, новая проверка
ожидает освобождения единственного слота ACME; завершение старого задания не
переносит её на старый срок. Конфигурация, использующая записываемую пару, также
ждёт завершения процесса. После удаления записи её отдельные файлы перестают
отслеживаться, если больше нигде не используются.

### Зашифрованные приватные PEM-ключи

Общая таблица `[tls]` доступна при `self`, `nginx`, `apache`, `litespeed` и `caddy`:

```toml
[server]
compatibility = "nginx" # также apache, litespeed или caddy
config = "nginx.conf"  # нативный файл выбранного адаптера

[tls]
password_file = "secrets/tls-passwords.txt"
```

Сертификат и зашифрованный ключ задаются обычными директивами выбранного сервера.
Для `self` пути и пароль можно указать в собственном формате:

```toml
[server]
compatibility = "self"

[http]
listen = "127.0.0.1:8443"
response = "ok\n"
http2 = true

[http.tls]
certificate = "certs/fullchain.pem"
key = "certs/private-encrypted.pem"
password_file = "secrets/tls-passwords.txt"
```

`http.tls.password_file` имеет приоритет над общим `tls.password_file`.
Оба TOML-пути разрешаются относительно `server.prefix`, а без него — каталога TOML.
Пустое значение пути запрещено. В nginx поддерживается `ssl_password_file FILE;`
в `http` и `server`: сервер наследует значение из `http`, собственная директива
заменяет его. Нативная директива имеет приоритет над общим TOML-значением и работает
также при прямом `-c nginx.conf`. Её относительный путь отсчитывается от каталога
основного nginx-конфига, как у `ssl_certificate_key`. Apache, OpenLiteSpeed и Caddy
получают пароль через общий `[tls]` в TOML; команды вроде Apache `SSLPassPhraseDialog`
для получения пароля не исполняются.

Файл содержит один пароль на строку. Допускаются LF, CRLF и последняя строка без
перевода строки. Пустые строки пропускаются; пробелы, кавычки и `#` — части пароля,
а не синтаксис комментариев или env-файла. Пароли пробуются последовательно для
каждого ключа: один файл может содержать разные пароли для SNI-сертификатов.
Поддерживаются зашифрованные PKCS#8 и традиционные PEM-ключи, читаемые OpenSSL.
Незашифрованные ключи продолжают работать без этой настройки.

Лимиты: обычный файл до 64 КиБ, до 64 непустых строк, до 1023 байт на пароль;
байт NUL запрещён. FIFO и устройства отклоняются без ожидания ввода. Ограничьте
доступ к файлу учётной записью сервера (например, права `0600`). Значения паролей
не включаются в `-T` и диагностику; временный буфер паролей очищается после загрузки
ключа, TLS-контекст не хранит ссылку на него.

Файл пароля автоматически отслеживается вместе с ключом, в том числе через symlink.
Неверный пароль, удаление, пустой или повреждённый файл сохраняют прежние TLS-контексты;
исправление только файла пароля запускает новую попытку. Для ротации можно сначала
записать в файл старый и новый пароль, затем заменить зашифрованный ключ и сертификат,
а после успешного reload удалить старый пароль. Для раздельного сохранения действует
тот же принцип: новая конфигурация применяется целиком только после проверки всех
TLS-пар. PID master не меняется; новые соединения используют новые контексты.
`server.auto_reload = false` отключает и наблюдение за паролями.

#### Отдельные файлы паролей для SNI-сертификатов

Для ручных ключей добавьте записи в TOML-обёртку любого режима совместимости:

```toml
[[tls.certificates]]
key = "certs/example.key"
password_file = "secrets/example.pass"

[[tls.certificates]]
key = "certs/api.key"
password_file = "secrets/api.pass"
```

Эти записи назначают пароли уже настроенным ручным ключам; сертификаты и виртуальные
хосты по-прежнему задаются нативным конфигом или `[http.tls]`. Оба пути отсчитываются
от `server.prefix`, а без него — от каталога TOML. Путь `key` после нормализации
`.`/`..` должен совпасть с путём ключа, полученным от адаптера. Symlink не раскрывается
при сопоставлении: укажите путь, используемый в конфигурации. Если один ключ используют
несколько виртуальных хостов, настройка применяется ко всем. Повторная запись для
того же ключа, неизвестный ключ, пустые или пропущенные поля — ошибки конфигурации.
Индивидуальная запись имеет приоритет над `http.tls.password_file`, nginx
`ssl_password_file` и общим `tls.password_file`.

У сертификатов Let's Encrypt пароль задаётся непосредственно в своей записи:

```toml
[[acme.certificates]]
name = "main"
domain = "example.com"
email = "admin@example.com"
accept_terms = true
password_file = "secrets/example.pass"

[[acme.certificates]]
name = "api"
domain = "api.example.com"
email = "admin@example.com"
accept_terms = true
password_file = "secrets/api.pass"
```

`acme.certificates.password_file` действует только для ключа этой записи и имеет
приоритет над настройками виртуального хоста и общим `[tls]`. Он также доступен
в одиночном `[acme]`. Для управляемых ключей используйте этот параметр, а не
`[[tls.certificates]]`. Если индивидуальной настройки нет, используется прежний
файл паролей виртуального хоста или общий файл. Пароли соседних SNI-записей никогда
не подставляются друг вместо друга.

Все используемые файлы паролей отслеживаются автоматически. Изменение содержимого,
замена пути в TOML и перестановка записей применяются через безопасный reload.
При ошибке любой пары сохраняется вся действующая конфигурация. Новый отсутствующий
файл продолжает отслеживаться после отклонённого reload: его создание повторяет
проверку. После успешного удаления или замены настройки старый файл перестаёт
отслеживаться, если его больше никто не использует. Удаление индивидуальной
настройки возвращает общий пароль; он тоже должен подходить к ключу.

Без `encrypt_key` файл пароля используется только загрузчиком TLS и не меняет
сроки проверки DNS/ACME. Автоматическое шифрование включается отдельно, как описано ниже.

#### Автоматическое шифрование ключей Let's Encrypt

Включите `encrypt_key = true` у нужных записей. Каждая такая запись требует свой
явно указанный `password_file`; общий `[tls]` не заменяет этот обязательный параметр.
Настройки работают в `self`, nginx, Apache, OpenLiteSpeed и Caddy, с HTTP-01 и DNS-01:

```toml
[[acme.certificates]]
name = "main"
domain = "example.com"
email = "admin@example.com"
accept_terms = true
encrypt_key = true
password_file = "secrets/example.pass"

[[acme.certificates]]
name = "api"
domain = "api.example.com"
email = "admin@example.com"
accept_terms = true
encrypt_key = true
password_file = "secrets/api.pass"
```

То же поле доступно в одиночном `[acme]`. По умолчанию `encrypt_key = false`, чтобы
существующие настройки загрузки зашифрованных ключей сохраняли своё поведение.
Файлы паролей создаются администратором; сервер не генерирует и не перезаписывает их.
Для шифрования берётся **первая непустая строка**. Остальные строки используются
для чтения предыдущего ключа при ротации. Пароли не передаются в аргументах команд,
окружении или журналах lego.

Lego выполняет выпуск/продление в отдельном временном каталоге с правами `0700`.
Там на время задания находятся незашифрованный ключ и служебные данные lego;
рабочая пара остаётся неизменной. После успешного выхода клиента сервер проверяет
цепочку сертификата и соответствие ключа, затем записывает зашифрованный PKCS#8:
PBES2, AES-256-CBC, PBKDF2-HMAC-SHA256, 200 000 итераций и случайная соль 16 байт.
Ключ записывается с правами `0600`, каталог поколения — `0700`.

Опубликованные пары находятся в `STORAGE/encrypted/NAME/current/NAME.crt` и `.key`.
`NAME` вычисляется из имён сертификата по обычным правилам ACME. `current` — ссылка
на полностью записанное поколение. После записи и синхронизации файлов ссылка
заменяется атомарно; только затем создаются новые TLS-контексты и плавно заменяются
workers. PID master остаётся прежним. Ошибка lego, неподходящая пара, ошибка
шифрования/записи, тайм-аут либо изменение пароля во время задания не публикуют
новую пару и сохраняют действующий HTTPS. Отменённый reload также не публикует
результат своего задания.

При обычном завершении, ошибке, тайм-ауте и остановке master временный каталог
удаляется. При тайм-ауте останавливается вся группа процессов задания. После
аварийного завершения остатки удаляются при следующем запуске задания этого
сертификата, когда освобождена блокировка; каталог работающего клиента не удаляется.
Удаление файлов не является гарантированным физическим стиранием данных на диске.
ACME-ключи учётной записи остаются под управлением lego в `STORAGE/accounts`;
`encrypt_key` относится к ключам сертификатов.

При включении `encrypt_key = true` существующая пара из
`STORAGE/certificates/NAME.crt` и `.key` автоматически переносится в зашифрованное
хранилище с собственным `password_file` записи. Это локальная операция: lego и CA
не вызываются, сертификат сохраняется побайтно, приватный ключ остаётся тем же.
Миграция работает при запуске и reload во всех режимах: `self`, nginx, Apache,
LiteSpeed и Caddy, включая SAN, wildcard и отдельные SNI-сертификаты. Работающее
задание старой конфигурации завершается до начала миграции. Если старого кеша нет,
выполняется обычный выпуск. Неполная пара, символьная ссылка вместо файла или
повреждённый ключ приводят к ошибке, а не к перевыпуску сертификата.

Старые файлы удаляются только после применения всей конфигурации: проверки TLS,
подготовки слушателей и запуска новых workers. Ошибка пароля, занятого порта или
другого сертификата сохраняет старый кеш и действующий HTTPS. До успешной очистки
можно вернуть прежнюю конфигурацию с `encrypt_key = false`. После очистки следует
использовать зашифрованное хранилище и файл пароля; автоматического обратного
экспорта незашифрованного ключа нет.

Очистка относится только к снимку файлов выбранного `NAME` с расширениями `.crt`,
`.key`, `.json`, `.issuer.crt`, `.pem`, `.pfx`. Файлы других сертификатов, учётных
записей и архивы lego сохраняются. Перед удалением сервер повторно проверяет
зашифрованную пару, содержимое и идентичность исходных файлов. Изменённый или
заменённый файл откладывает очистку этой записи; другие записи могут завершить
миграцию независимо. Очистка также откладывается, если активный ручной TLS-хост
ещё ссылается на старый сертификат или ключ, в том числе через файловый псевдоним.
Отложенная очистка записывается в журнал.

Манифест `NAME.migration.json` в зашифрованном поколении позволяет продолжить
очистку после ошибки или перезапуска. При удалении файлы сначала перемещаются в
закрытый каталог `STORAGE/encrypted/NAME/cleanup`, повторно проверяются и удаляются.
Оставшиеся после прерывания файлы обрабатываются при следующей успешной активации.
Изменённый файл возвращается на прежнее место, если оно свободно; иначе сохраняется
в `cleanup` для восстановления. При включённом `auto_reload` исправление старых
файлов или удаление ручной ссылки из конфигурации запускает повторную попытку.
При выключенном — нужен reload через SIGHUP. Удаление означает unlink файлов,
без гарантии физического стирания на SSD или удаления резервных копий.

Уже существующее зашифрованное хранилище имеет приоритет: оно не перезаписывается
старым кешем. Без манифеста миграции старые файлы автоматически не удаляются.
Первая плановая проверка перенесённого сертификата откладывается на
`check_interval`, затем продление работает в обычном режиме.

Для смены пароля сначала запишите новый пароль первой строкой, старый — второй.
При `encrypt_key = true` изменение отслеживаемого файла или его пути запускает
локальное перешифрование только соответствующего SNI-ключа. Lego и CA не вызываются,
даже если сертификат уже попадает в окно продления. Сертификат сохраняется побайтно,
ключевой материал остаётся тем же, меняется только пароль шифрования. Механизм
одинаков для `self`, nginx, Apache, LiteSpeed и Caddy. Сервер не генерирует пароли
по таймеру и не перезаписывает файл пароля.

После проверки всех пар публикуется зашифрованное поколение и выполняется безопасный
reload. Сообщение `re-encrypted ACME key ... locally; certificate unchanged`
подтверждает перешифрование, а `reload complete` — применение конфигурации. До
успешного reload сохраняйте обе строки: публикация пары может предшествовать ошибке
подготовки слушателей, при этом действующие TLS-контексты продолжают обслуживать
соединения. После успешного reload можно удалить старую строку. Удаление запасных
паролей само по себе не перешифровывает ключ повторно и не запускает ACME-проверку.

Если убрать старый пароль до перешифрования, сервер не сможет прочитать прежний
ключ: reload отклоняется до восстановления пароля. Пустой, отсутствующий или
изменившийся во время перешифрования файл также не применяется. Работающее
ACME-задание завершается до локальной ротации. При `auto_reload = false` изменения
применяются через SIGHUP; запуск сервера тоже проверяет необходимость перешифрования.
`-t` только проверяет конфигурацию и не меняет ключи.

Изменение пароля сохраняет сроки плановых ACME-проверок всех записей, включая
ротируемую. Плановое продление работает независимо; изменение `renew_before_days`
или `check_interval_seconds` явно ставит проверку соответствующей записи в очередь.
Проверка без изменений не переписывает ключ и не вызывает цикл reload.

После успешной активации конфигурации сервер удаляет старые зашифрованные
поколения каждого SNI-сертификата из `STORAGE/encrypted/NAME`. Это относится и к
ротации пароля, и к продлению. `current` сохраняется; его имя, содержимое пары и
файл пароля сверяются со снимком, сделанным при подготовке новых TLS-контекстов.
При неудачном reload старые поколения остаются, в том числе при нескольких
последовательных попытках ротации. Подготовка очередного ACME-задания больше не
удаляет опубликованные поколения.

Очистка выполняется под блокировкой записи после запуска новых workers. Каталог
старого поколения получает журнал `retirement.json` с идентичностями и SHA-256
его файлов, затем переименовывается из `gen-XXXXXX` в `.retired-gen-XXXXXX`.
Записи каталога и журнал синхронизируются на диск до удаления файлов. После
прерывания следующий успешный reload или запуск продолжает очистку: уже удалённые
файлы пропускаются, перемещённые в `.unlink-N` проверяются повторно. Журнал
удаляется последним. Старые поколения, созданные предыдущей версией, также
обрабатываются, если имеют штатное имя и известный набор файлов.

Символьные ссылки вместо каталогов или файлов не обходятся. Неизвестные файлы,
повреждённый журнал либо изменение записанного в журнале файла откладывают
удаление этого поколения и выводят предупреждение; другие поколения и SNI-записи
могут очищаться независимо. Если активный ручной TLS-хост ещё использует старый
сертификат или ключ, в том числе через ссылку, поколение сохраняется. Учитываются
и файлы, фактически загруженные при активации: перенаправление ссылки с последующим
неудачным reload не разрешает удалять используемое поколение. Работающие старые workers используют уже
загруженные TLS-контексты и завершают соединения плавно. Удаление выполняется через
unlink и не гарантирует физического стирания на SSD или очистки резервных копий.

Отложенная очистка автоматически повторяется master-процессом отдельно для каждой
SNI-записи. Задержки между попытками составляют 1, 2, 4, 8, 16 и затем максимум
30 секунд. Исправление файла журнала, восстановление исходного файла, устранение
ошибки доступа или освобождение блокировки не требуют SIGHUP либо изменения
`config.toml`. Неисправная запись не блокирует очистку остальных. После успеха
опрос этой записи прекращается; очередная активация снова проверяет старые поколения.
После перезапуска повтор восстанавливается из каталогов и журналов очистки.

Повторы работают и при `server.auto_reload = false`, не обращаются к CA, не меняют
сертификаты, пароли или workers и не инициируют reload. Они используют только
успешно активированную конфигурацию и её снимок ключей. Во время подготовки новой
конфигурации очистка приостанавливается; запись с работающим ACME-клиентом пропускается.
Если поколение ещё используется ручным TLS-хостом, нужна активация конфигурации,
которая больше на него не ссылается: таймер не применяет изменения конфигурации
самостоятельно. При повторах в рамках одной активной конфигурации одинаковая
ошибка не записывается в журнал повторно до её смены;
завершение отложенной очистки отмечается сообщением
`encrypted generation cleanup ... completed after retry`.

`-t` проверяет файл пароля даже до первого выпуска, не обращается к CA и не
мигрирует и не удаляет файлы. Добавление новой записи через reload сначала
проверяет пароль, затем мигрирует старую пару либо выпускает и шифрует сертификат;
рабочая конфигурация применяется после готовности всех пар.
`server.auto_reload = false` отключает отслеживание файлов, но не плановое
продление и публикацию зашифрованных ключей.

## Собственный формат HTTP

```toml
[server]
compatibility = "self"

[http]
listen = "127.0.0.1:8080"
response = "zhttpd\n"
http2 = false
http3 = false
max_body_size = 1_048_576
keepalive_timeout_ms = 75_000

[[http.routes]]
path = "/health"
match = "exact"
response = "ok\n"
status = 200

[[http.routes]]
path = "/assets/"
root = "public"

[[http.routes]]
path = "/api/"
proxy = "http://127.0.0.1:9001/"

[[http.routes]]
path = "/socket"
match = "exact"
websocket = true
```

| Поле | Значение и поведение |
| --- | --- |
| `http.listen` | Обязательный IP/localhost/wildcard и порт; IPv6 в `[::1]:8080` |
| `http.root` | Корень статических файлов; URI `/assets/a.css` ищет `ROOT/assets/a.css` |
| `http.response` | Текст резервного ответа 200; несовместим с `http.root` и prefix-маршрутом `/` |
| `http.index` | Имя индексного файла; по умолчанию `index.html` |
| `http.http2` | HTTP/2 через TLS и ALPN; по умолчанию false |
| `http.http3` | Дополнительный QUIC/UDP listener на том же адресе и порту; по умолчанию false |
| `http.max_body_size` | Максимальный размер тела запроса в байтах; по умолчанию 1048576; 0 снимает ограничение |
| `http.keepalive_timeout_ms` | Таймаут keep-alive и бездействия WebSocket; по умолчанию 75000 |
| `routes.path` | Обязательный путь, начинающийся `/` |
| `routes.match` | `prefix` по умолчанию или `exact`; exact имеет приоритет, затем самый длинный prefix |
| `routes.status` | 200–599, только с `response`; по умолчанию 200 |

Каждый маршрут имеет **ровно одно** действие: `response`, `root`, `proxy`,
`websocket=true`, `fastcgi` или `wsgi`. Неизвестные поля и повторные маршруты
одного вида — ошибки. Без `root`/`response` и резервного prefix `/` ответ — 404.
Текущая нативная схема описывает один виртуальный сервер и один TCP-адрес;
виртуальные хосты доступны через адаптеры.

### TLS, HTTP/2 и HTTP/3

```toml
[http]
listen = "0.0.0.0:8443"
response = "secure\n"
http2 = true
http3 = true

[http.tls]
certificate = "certs/fullchain.pem"
key = "certs/key.pem"
```

Оба пути TLS обязательны вместе. HTTP/2 и HTTP/3 требуют TLS и сборку
`mise run build`. HTTP/2 без TLS (h2c), WebSocket extended CONNECT, server push
и передача request trailers обработчикам пока не реализованы. Нативный формат
не добавляет Alt-Svc автоматически: HTTP/3-клиент должен знать адрес; nginx
адаптер позволяет объявить `add_header Alt-Svc 'h3=":8443"' always`.

### FastCGI и WSGI

```toml
[[http.routes]]
path = "/php/"
fastcgi = "127.0.0.1:9000"

[[http.routes]]
path = "/app/"
wsgi = "127.0.0.1:9002"
```

FastCGI v1, роль Responder: TCP, отдельное соединение на запрос, тело запроса
буферизуется в пределах `max_body_size`, ответ передаётся потоком. Поддержаны
PARAMS, STDIN, STDOUT, STDERR (дренируется, не становится ответом), END_REQUEST,
CGI `Status`, Content-Type и Content-Length. Ошибка соединения/протокола даёт 502,
таймаут — 504; после начала ответа соединение закрывается. Unix-сокеты,
мультиплексирование и повторное использование FastCGI-соединений не реализованы.

`SCRIPT_FILENAME` строится из `http.root` и нормализованного URI. Заголовок Proxy
не превращается в HTTP_PROXY. Для WSGI SCRIPT_NAME пуст, PATH_INFO содержит
полный путь запроса, включая `/app/`: префикс не отрезается.

Python-шлюз работает отдельным процессом и использует стандартный
`wsgiref.handlers.BaseCGIHandler` для PEP 3333. Запуск примера:

```sh
mise run wsgi -- --port 9002 --app-dir examples/wsgi --app app:application
```

Процесс шлюза запускает оператор или менеджер процессов. Шлюз обслуживает до
32 запросов одновременно, допускает до 16 MiB тела и 128 KiB параметров,
поддерживает `start_response`, `write`, итераторы, `close`, обработку исключений.
Он предназначен для доверенного локального FastCGI-соединения.

## Журналы

```toml
[logging]
access = "logs/access.log" # также stdout, stderr, off
format = "json"            # combined, common, json
error = "stderr"
level = "warn"             # emerg, alert, crit, error/err, warn, notice, info, debug
```

Каталоги журналов должны существовать. Файлы открываются с O_APPEND; сигнал
USR1 переоткрывает журналы рабочих процессов после внешней ротации. Настройка
`logging.access` заменяет access-журналы во всех импортированных locations.
`logging.error` и `logging.level` задают общий журнал и его порог; отдельные
server/location error-журналы адаптера имеют приоритет. `server.error_log`
поддерживается как более ранний вариант общего пути, `[logging].error` сильнее.

JSON — стабильная схема zhttpd: `time`, `remote_addr`, `method`, `uri`, `protocol`,
`status` (число), `bytes` (число), `duration` (секунды). Ошибки используют общий
текстовый формат zhttpd. Подробности импорта журналов — в
[совместимости](compatibility.md).

## Автоматический Let's Encrypt

```toml
[server]
compatibility = "self"

[http]
listen = "0.0.0.0:443"
response = "secure\n"
http2 = true
http3 = true

[acme]
domain = "example.com"
email = "admin@example.com"
accept_terms = true
storage = ".acme"
# Сначала можно проверить выпуск через staging:
# directory = "https://acme-staging-v02.api.letsencrypt.org/directory"
# client = "lego"
# http_port = 80
# renew_before_days = 30
# check_interval_seconds = 43200
```

Используется lego 5.6.0 из mise. Первый запуск без сертификата выпускает его
до открытия HTTPS. Затем управляющий процесс проверяет обновление каждые
12 часов; при изменении сертификата перезагружает рабочие процессы. При ошибке
обновления текущая TLS-конфигурация продолжает работать, повторная попытка —
не позднее чем через час. `operation_timeout_seconds` ограничивает задание ACME
(по умолчанию 600 секунд). `-t` не
выпускает сертификаты; если они уже есть, проверяет их загрузку. До первого
выпуска проверка пропускает только загрузку управляемого сертификата; TLS-опции
и ручные сертификаты других виртуальных хостов проверяются всегда.

HTTP-01 и DNS-01 работают во всех режимах: `self`, `nginx`, `apache`,
`litespeed`, `caddy`. `domain = "example.com"` — сохранённая сокращённая запись
для одного имени. Для нескольких имён задайте однострочный массив
`domains = ["example.com", "www.example.com", "other.net"]`; одновременно
`domain` и `domains` указывать нельзя. Все имена `[acme]` входят в **один SAN-сертификат**. Для отдельных
сертификатов используйте `[[acme.certificates]]`, описанный ниже.
Пустой список, повторы без учёта регистра и некорректные DNS-имена отклоняются.
IDN задаются в ASCII/Punycode; завершающая точка не допускается.

По умолчанию `challenge = "http-01"`. Каждое имя должно разрешаться на сервер,
входящий TCP 80 должен быть доступен lego. Этот порт зарезервирован: zhttpd
не может слушать его одновременно. `http_port` меняет локальный порт lego;
при нестандартном порте оператор перенаправляет на него публичный TCP 80.
Привилегии на привязку к портам настраивает оператор. HTTPS directory обязателен.

`[acme]` несовместим с ручными `[http.tls]` путями. Сертификат и ключ сохраняются
в `STORAGE/certificates/NAME.crt` и `.key`; учётная запись — в том же storage.
Для одного имени NAME равен домену (`*` заменяется на `_`), для нескольких —
`san-` плюс SHA-256 отсортированных нормализованных имён, каждое с завершающим `\n`.
Перестановка имён сохраняет кеш; изменение набора создаёт отдельный сертификат,
чтобы при запуске не использовать старые SAN. Старые файлы автоматически не удаляются.
Изменение набора имён, добавление и удаление сертификатов применяются через
`SIGHUP` или `-s reload` без перезапуска master-процесса. Недостающие сертификаты
выпускаются в фоне до переключения конфигурации; подробнее — ниже.
Запускайте сервер через `mise exec -- …` или укажите полный путь `acme.client`.
Реальный выпуск требует явного `accept_terms=true`.

### Wildcard и DNS-01

```toml
[acme]
domains = ["example.com", "*.example.com", "api.other.net"]
email = "admin@example.com"
accept_terms = true
challenge = "dns-01"
dns_provider = "cloudflare"
storage = ".acme"
# directory = "https://acme-staging-v02.api.letsencrypt.org/directory"
# dns_resolvers = ["1.1.1.1:53", "8.8.8.8:53"]
# operation_timeout_seconds = 600
```

Wildcard требует DNS-01. `*.example.com` покрывает `www.example.com`, но не
`example.com` и не `a.b.example.com`; добавьте apex отдельным элементом, если он
тоже нужен. DNS-01 не открывает и не резервирует HTTP-порт: `http_port` в этом
режиме не используется. lego создаёт TXT-записи `_acme-challenge`, ожидает
распространения DNS, затем удаляет записи. Поведение challenge описано в
[документации Let's Encrypt](https://letsencrypt.org/docs/challenge-types/#dns-01-challenge).

`dns_provider` — код автоматического провайдера из установленного lego;
интерактивный `manual` запрещён. Один провайдер обслуживает весь SAN-набор:
его учётные данные должны разрешать изменение всех нужных DNS-зон.
Список провайдеров и обязательные переменные:

```sh
mise exec -- lego dnshelp
mise exec -- lego dnshelp --code cloudflare
```

Секреты передаются в окружении процесса zhttpd, наследуемом lego, либо через
`dns_env_file` конкретного сертификата. В TOML записывается только путь к файлу,
а не сами секреты; в аргументах команды также передаётся только путь. Например, для Cloudflare задайте
`CF_DNS_API_TOKEN_FILE=/absolute/private/cloudflare-token`; содержимое файла —
токен с Zone:Read и DNS:Edit для нужных зон. Поддерживается и `CF_DNS_API_TOKEN`.
См. [Cloudflare в lego](https://go-acme.github.io/lego/dns/cloudflare/) и
[другие провайдеры](https://go-acme.github.io/lego/dns/).

`dns_resolvers` — необязательный однострочный массив адресов рекурсивных DNS
(например, `host:port` или `[IPv6]:port`); по умолчанию lego использует системные.
Таймаут распространения и интервалы опроса задаются переменными выбранного
провайдера. `operation_timeout_seconds` должен учитывать все имена и ожидание DNS.
Дополнительная настройка `dns_propagation_wait_seconds` по умолчанию равна 0:
lego проверяет распространение. Положительное значение **заменяет проверки lego
фиксированным ожиданием**; CA всё равно проверяет TXT. Используйте это только
при намеренном отключении предварительных DNS-проверок, например в локальном
тестовом стенде. Значение должно быть меньше `operation_timeout_seconds`.
DNS-настройки при `http-01` отклоняются. `-t` проверяет синтаксис, но не обращается
к API провайдера и не проверяет его учётные данные; ошибки провайдера видны при выпуске.

### Отдельные сертификаты и SNI

`[[acme.certificates]]` работает в `self`, nginx, Apache, OpenLiteSpeed и Caddy.
Каждая запись описывает независимый сертификат: свой SAN-набор, DNS-провайдер,
учётные данные, ACME directory, storage и расписание продления. Например:

```toml
[server]
compatibility = "nginx"
config = "nginx.conf"

[[acme.certificates]]
name = "main"
domains = ["example.com", "*.example.com"]
email = "admin@example.com"
accept_terms = true
challenge = "dns-01"
dns_provider = "cloudflare"
dns_env_file = "secrets/cloudflare.env"
storage = ".acme"

[[acme.certificates]]
name = "other"
domains = ["other.net"]
email = "admin@example.com"
accept_terms = true
challenge = "dns-01"
dns_provider = "route53"
dns_env_file = "secrets/route53.env"
storage = ".acme"
```

У каждой записи обязательны уникальный `name` (буквы ASCII, цифры, `_`, `-`),
`domain` или `domains`, контактный email и `accept_terms=true`. Остальные поля
имеют те же значения по умолчанию, что и в `[acme]`. Настройки между записями
не наследуются. Старый `[acme]` поддерживается; его настройки нельзя смешивать
с `[[acme.certificates]]`. Модуль по-прежнему отключается через `modules.acme=false`.

SNI выбирает сертификат среди назначенных виртуальному хосту: точное SAN-имя
имеет приоритет перед wildcard независимо от порядка записей. Поэтому можно
добавить отдельный сертификат для `api.example.com`, оставив `*.example.com`
для остальных поддоменов. Одинаковое SAN-имя в двух сертификатах запрещено;
`*.example.com` и `api.example.com` считаются разными именами и допускаются.
Правило одного уровня wildcard сохраняется.

Имена одного виртуального хоста могут обслуживаться разными сертификатами:
например, nginx `server_name example.com *.example.com other.net;`.
HTTP-маршруты остаются общими, сертификат выбирается во время TLS handshake.
Отдельные виртуальные хосты на одном сокете также поддерживаются. Все aliases
управляемого хоста должны покрываться объединением его сертификатов.
Ручные сертификаты посторонних виртуальных хостов сохраняются.
В `self` все записи назначаются общему HTTPS listener.
Без SNI или при неизвестном имени используется первый назначенный сертификат
виртуального хоста по умолчанию; изменение порядка может изменить этот fallback.
Выбор SNI применяется к TLS для HTTP/1.1, HTTP/2 и HTTP/3.

`dns_env_file` — необязательный путь к dotenv-файлу, относительно корня
конфигурации, как `storage`. Он поддерживается и в старом `[acme]` при DNS-01.
Файл должен быть доступным, непустым и не больше 1 MiB. `-t` проверяет доступность
файла без обращения к DNS API; lego разбирает его при запуске задания.
Отсутствующий файл — ошибка, подмена общим окружением не выполняется.
В lego 5.6.0 значения dotenv переопределяют одноимённые переменные окружения
только в дочернем процессе; остальные переменные наследуются. Это позволяет
использовать как разные провайдеры, так и разные аккаунты одного провайдера.
Каждое задание читает свой файл заново. Формат описан в
[документации lego](https://go-acme.github.io/lego/dns/#dotenv-file).

Пример `cloudflare.env`:

```dotenv
CF_DNS_API_TOKEN=YOUR_CLOUDFLARE_TOKEN
```

Пример `route53.env`:

```dotenv
AWS_ACCESS_KEY_ID=YOUR_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY=YOUR_SECRET_ACCESS_KEY
AWS_REGION=us-east-1
```

Права и альтернативные способы авторизации описаны у
[Cloudflare](https://go-acme.github.io/lego/dns/cloudflare/) и
[Route 53](https://go-acme.github.io/lego/dns/route53/).
Храните реальные env-файлы вне git, с доступом только пользователю сервера.
Для каждого SAN-набора нужен доступ ко всем его DNS-зонам через выбранный провайдер.
Можно сочетать HTTP-01 и DNS-01 в разных записях; DNS-поля разрешены только у DNS-01.

При первом запуске недостающие сертификаты выпускаются последовательно до
открытия HTTPS. Ошибка первоначального выпуска прерывает запуск.
Затем каждый сертификат имеет собственный срок проверки, повторной попытки
и `operation_timeout_seconds`. Одновременно запускается одно задание lego:
это позволяет использовать общий HTTP-01 порт и storage без конфликтов.
После завершения или таймаута неудачного задания очередь продолжает работу;
действующие TLS-сертификаты сохраняются, другие сертификаты продлеваются.
Обновление сертификата перезагружает рабочие процессы, сохраняя сроки остальных
заданий. Перестановка записей при SIGHUP не меняет принадлежность выполняющегося
задания. Добавление SAN и новых сертификатов поддерживается через reload,
включая первоначальный выпуск отсутствующих файлов.

`name` используется в диагностике, а пути сертификатов по-прежнему определяются
SAN-набором и `storage`; переименование записи не вызывает перевыпуск.
Полные конфиги пяти режимов: [examples/acme/sni](../examples/acme/sni/README.md).

### Добавление и удаление через reload

Это работает одинаково в режимах `self`, `nginx`, `apache`, `litespeed`, `caddy`,
для одиночного `[acme]` и списка `[[acme.certificates]]`, HTTP-01 и DNS-01.

При включённом `server.auto_reload` сохранение этих файлов автоматически
запускает описанный ниже процесс; вручную отправлять сигнал не нужно.

1. Обновите записи сертификатов в `config.toml`. В режиме совместимости также
   измените имена/виртуальные хосты в нативном конфиге сервера. Каждый HTTPS-хост
   должен оставаться покрыт сертификатом либо иметь ручные пути TLS.
2. Если автоматическое наблюдение отключено, проверьте конфигурацию и отправьте reload:

   ```sh
   mise exec -- zig-out/bin/zhttpd -c /path/to/config.toml -t
   mise exec -- zig-out/bin/zhttpd -c /path/to/config.toml -s reload
   ```

   Требуется настроенный `[server] pid`; альтернативно — `kill -HUP <master-pid>`.
   Проверка `-t` не выпускает сертификаты и допускает отсутствие новых managed-файлов.
3. Следите за журналом master: `issuing reload ACME certificate` означает выпуск,
   `reload complete` — включение новой конфигурации. Команда `-s reload` только
   отправляет сигнал, её успешный выход не означает завершение выпуска.

Master сохраняет текущую конфигурацию и обслуживает запросы, пока lego
последовательно выпускает недостающие сертификаты с DNS-провайдером и env-файлом
каждой записи. Новые workers запускаются после готовности **всех** сертификатов
и проверки TLS/слушающих сокетов; прежние workers завершаются плавно.
Новые соединения используют обновлённые SNI и маршруты. Уже открытые соединения
могут завершить работу с прежним сертификатом.

При ошибке конфигурации, выпуска или `operation_timeout_seconds` действующая
конфигурация сохраняется целиком, включая записи, предложенные к удалению.
Исправьте причину и повторите reload. Автоматическое продление действующих
сертификатов продолжается; оно не применяет отклонённые изменения с диска.
Повторный reload заменяет ожидающую конфигурацию. Уже запущенное устаревшее
задание может завершить выпуск и очистку DNS, но не включит свою конфигурацию.
Следующий выпуск ждёт освобождения единственного слота ACME.

Удаление записи убирает её из SNI и очереди продления после успешного reload.
Файлы, аккаунты ACME и выпущенные сертификаты не удаляются и не отзываются;
повторное добавление может использовать кеш. Изменение SAN создаёт новый ключ
кеша, поэтому может потребовать выпуска, в том числе при удалении части имён.
HTTP-01 порт должен быть свободен и в новой, и в ещё действующей конфигурации:
reload не может занять порт, который прежние workers продолжают обслуживать.

### ACME с конфигурацией другого сервера

Один и тот же раздел `[acme]` работает со всеми адаптерами:

```toml
[server]
compatibility = "nginx" # apache, litespeed или caddy
config = "nginx.conf"  # путь к исходному конфигу выбранного формата

[acme]
domain = "example.com"
email = "admin@example.com"
accept_terms = true
storage = ".acme"
```

В исходном конфиге укажите **HTTPS** и имена из `acme.domains` (или `acme.domain`):

| Режим | Выбор виртуального хоста |
| --- | --- |
| nginx | `listen 443 ssl;` и `server_name example.com;` |
| Apache | `Listen 443`, `<VirtualHost *:443>`, `SSLEngine on`, `ServerName example.com` |
| OpenLiteSpeed | `listener` с `secure 1` и `map site example.com` |
| Caddy | site `https://example.com` (или `example.com`) |

Пути ручных сертификатов можно не задавать. После импорта ACME назначает
свои certificate/key совпавшим HTTPS-хостам; если там уже указаны
ручные пути, `[acme]` имеет приоритет. Конфиги на диске не переписываются.
Другие хосты сохраняют свои TLS-настройки и сертификаты, включая хосты на том
же сокете. Совпадение не зависит от регистра. Точный хост также может быть
покрыт wildcard-сертификатом. Wildcard-хост `*.example.com` требует такого же
wildcard в SAN. Для nginx используйте `server_name example.com *.example.com;`,
для Apache — `ServerName example.com` и `ServerAlias *.example.com`, для
OpenLiteSpeed — `map site example.com,*.example.com`, для Caddy —
`https://example.com, https://*.example.com { … }`.

Все имена выбранного виртуального хоста должны покрываться SAN назначенных сертификатов: частично
покрытые aliases вызывают ошибку. Regex, завершающий wildcard (`www.*`) и
сокращение nginx `.example.com` не используются для назначения ACME-сертификата;
укажите точные имена и `*.example.com` явно. Имена из исходных конфигов
автоматически в SAN не добавляются. В `self` весь набор назначается общему
HTTPS listener. `[acme]` задаёт один сертификат для нескольких виртуальных
хостов; `[[acme.certificates]]` задаёт отдельные сертификаты с выбором через SNI.

Отсутствие совпадающего HTTPS-хоста, `ssl_reject_handshake on` у выбранного
хоста или конфликт с портом HTTP-01 — ошибки конфигурации. Plain HTTP listeners
не превращаются в HTTPS автоматически. В Caddy `[acme]` действует и на
импортированные Caddyfile-файлы. Без `[acme]` HTTPS по-прежнему требует ручных
сертификатов. Прямой запуск `-c nginx.conf` не включает ACME: для автоматического
выпуска используйте TOML-обёртку.

Полные примеры: [examples/acme](../examples/acme/README.md).

## Синтаксис

Поддерживается строгая прикладная часть TOML: перечисленные таблицы,
`[[http.routes]]`, `[[acme.certificates]]`, `[[tls.certificates]]`, однострочные строки в одинарных/двойных кавычках, escape и
Unicode в basic strings, boolean, неотрицательные десятичные целые с `_`,
однострочные массивы строк для `domains` и `dns_resolvers` в настройках ACME, комментарии.
Не поддерживаются произвольные/многострочные массивы, inline tables, даты,
float, многострочные строки и quoted keys. Неизвестные/повторные таблицы и
ключи отклоняются. Размер TOML ограничен 1 MiB.
