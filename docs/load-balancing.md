# Балансировка по нагрузке

Модуль `load_balancer` выключен по умолчанию. Он независимо импортируется из Zig
и подключён к HTTP runtime через `http.load_balancer` / `zhttpd.load_balancer`.
Политика выбора и URL находятся в `src/load_balancer.zig`, POSIX-сборщик метрик
и общий файловый бэкенд — в `src/load_balancer/backend.c`.

Для обмена без общего filesystem доступен [Raft companion](raft.md): он
согласовывает конфигурацию, участников и метрики через большинство. В этом
режиме `publish_backend` указывает на локальный inbox, а `backend` — на
каталог подтверждённых данных.

## Настройка двух инстансов

Создайте каталог метрик, доступный всем инстансам под одним сервисным UID.
На одном хосте достаточно локального каталога; на разных хостах нужен общий
том с атомарным `rename` внутри каталога и согласованными часами. Путь может
отличаться между хостами, но должен указывать на один и тот же каталог.
Каталог должен быть отдельным для этого кластера и доступным на запись только
доверенным инстансам. Файлы создаются с правами `0600`.

Пример для первого инстанса:

```toml
[server]
compatibility = "self"

[http]
listen = "127.0.0.1:8081"
response = "hello from node-a"

[load_balancer]
enabled = true
node_id = "node-a"
backend = "/srv/zhttpd/cluster-metrics"
node_ids = ["node-a", "node-b"]
node_urls = ["http://127.0.0.1:8081", "http://127.0.0.1:8082"]
max_connections = 400
memory_limit_mb = 512
cpu_capacity = 2
threshold_percent = 80
min_improvement_percent = 10
interval_ms = 1000
ttl_ms = 5000
```

На втором инстансе измените `node_id` на `node-b`, `http.listen` на
`127.0.0.1:8082` и текст ответа. В реальном кластере `node_urls` должны содержать
прямые HTTP(S)-адреса узлов, доступные клиентам, с одинаковым приложением,
маршрутами и политикой доступа. Не указывайте адрес общего балансировщика.
У всех узлов должны быть одинаковые списки соответствий ID → URL; собственные
лимиты могут различаться. Параметры применяются ко всем виртуальным хостам
инстанса. Для приложений с несколькими независимыми виртуальными хостами нужны
отдельные группы инстансов с подходящими публичными адресами.

Таблица `[load_balancer]` также работает в TOML-обёртке над nginx, Apache,
OpenLiteSpeed и Caddy. Относительный `backend` разрешается от server prefix
(по умолчанию каталога TOML). `modules.load_balancer = false` запрещает
включение модуля. Отсутствие `[load_balancer]` оставляет прежнее поведение.

| Параметр | Значение |
| --- | --- |
| `node_id` | Уникальный ID живого инстанса, 1–63 ASCII-буквы, цифры, `_` или `-` |
| `node_ids`, `node_urls` | От 2 до 32 соответствующих элементов; URL только origin, без пути, query, fragment и userinfo |
| `max_connections` | Обязательный ненулевой лимит нагрузки для всего инстанса; не меняет `worker_connections` |
| `memory_limit_mb` | Обязательный ненулевой бюджет суммарного RSS workers в MiB |
| `cpu_capacity` | Выделенное инстансу число CPU-ядер, по умолчанию 1; учитывайте контейнерные квоты вручную |
| `threshold_percent` | 1–100, по умолчанию 80; перенаправление только при превышении |
| `min_improvement_percent` | 1–100 процентных пунктов, по умолчанию 10; минимальная разница нагрузки |
| `interval_ms` | Период сбора и обмена: 100–60000 мс, по умолчанию 1000 |
| `ttl_ms` | 3000–300000 мс, минимум три интервала; по умолчанию 5000 |

## Метрики и выбор узла

Каждый worker публикует отдельный heartbeat через временный файл и атомарный
`rename`. Сборщик в фоновом потоке читает записи всех настроенных инстансов
и суммирует их workers. HTTP event loop только обновляет атомарный счётчик
и читает снимок в памяти, без дисковых или сетевых ожиданий. Если снимок в этот
момент обновляется, запрос обрабатывается локально.

Метрики:

- Активные слоты `Worker.nconns`: TCP-соединения, включая keep-alive, и внутренние
  соединения для HTTP/2 и HTTP/3 streams. Это тот же учёт ресурсов, который
  ограничивает `worker_connections`; это не счётчик физических QUIC-соединений.
- CPU workers: прирост user+system CPU seconds за интервал, делённый на реальное
  прошедшее время. Одно полностью занятое ядро даёт 1.0. Процессы master и другие
  приложения хоста не включаются.
- Текущий RSS workers: `/proc/self/statm` на Linux, `task_info` на macOS.
  Общие страницы между workers могут учитываться несколько раз. Если RSS
  недоступен, узел не считается кандидатом с нулевой нагрузкой.

Итоговая нагрузка:

```text
max(сумма соединений / max_connections,
    сумма CPU / cpu_capacity,
    сумма RSS / memory_limit_mb)
```

При превышении порога выбирается узел с наименьшей нагрузкой, строго ниже
порога и с достаточной разницей. Каждый узел оценивается относительно своих
лимитов. Текущий узел и HTTP-адреса при HTTPS-запросе исключаются.

Просроченные, повреждённые и неполные снимки не используются. Должны присутствовать
свежие записи как минимум ожидаемого количества workers. После остановки,
потери бэкенда или его зависания ранее полученные снимки истекают по монотонным
часам, даже если сборщик ещё не вернулся. Фоновый сборщик также проверяет
heartbeat event loop, чтобы зависший worker не публиковал здоровое состояние
бесконечно. При недоступном бэкенде или отсутствии подходящего узла запрос
обрабатывается локально. Это балансировка нагрузки, а не механизм жёсткого
ограничения запросов или активная проверка приложения HTTP-пробами.

Поддерживается до 256 workers на инстанс. При reload старые workers остаются
в сумме, пока обслуживают соединения; при изменении лимитов неоднородные записи
временно исключают узел. Graceful shutdown удаляет собственный файл worker.
После `SIGKILL` файлы остаются, но истекают по TTL. Каталог ограничен 4096
элементами на сканирование: превышение отключает выбор узлов до очистки.
Удаляйте остатки завершённых процессов при обслуживании кластера; не удаляйте
записи живых workers. Зависший общий filesystem не блокирует HTTP, но может
задержать graceful shutdown сборщика до возврата файловой операции.

## HTTP 307 и защита от циклов

Сервер отвечает `307 Temporary Redirect`, `Location` и `Cache-Control: no-store`
до исполнения обработчика приложения. HTTP/1-соединение закрывается, поэтому
большое тело и `Expect: 100-continue` не требуется сначала дочитывать на
перегруженном узле. Клиент, следующий 307, повторяет исходный метод и тело.
Реализован режим редиректа; внутреннего проксирования между узлами здесь нет.

К исходному raw URL добавляется `__zhttpd_lb=1`. Например:

```text
POST /upload?name=a%2Fb
307 Location: https://node-b.example/upload?name=a%2Fb&__zhttpd_lb=1
```

Принимающий узел распознаёт маркер, удаляет добавленный суффикс из target/query
и обрабатывает запрос локально **без повторной балансировки**, даже если уже
сам перегружен. Метод, тело, percent encoding и порядок исходных параметров
сохраняются. Защита не зависит от переноса произвольного response header
клиентом. Для балансировки разрешён ровно один переход; обычные редиректы самого
приложения имеют собственную семантику.

Имя `__zhttpd_lb` зарезервировано. Наличие любого его значения запрещает
балансировку; неизвестные значения не интерпретируются как адрес или разрешение
доступа. Это не аутентификационный токен. Клиент может сам запросить локальную
обработку, как и при отсутствии здорового соседа. Origin-form URL с fragment
и absolute-form request targets остаются локальными.

Клиент и промежуточные прокси должны сохранять служебный параметр. Приложения
с подписями URL или внешними редиректами, копирующими только часть query, требуют
учёта этого механизма. При переходе на другой origin клиент может не переносить
cookies или Authorization; настройте общую модель сессий приложения. 307
гарантирует сохранение метода и тела по протоколу, но не автоматический перенос
учётных данных между хостами. Не используйте общий файловый бэкенд как публичный
источник произвольных redirect URL: адреса берутся только из конфигурации.

## Проверка

```bash
zig build test-load-balancer
zig build test-load-balancer-e2e
zig build test
```

E2E требует Python standard library и `curl`. Запускает два настоящих инстанса,
проверяет суммирование двух workers, POST/PUT/PATCH/DELETE и бинарное тело,
`Expect: 100-continue`, смену нагрузки между переходами, TTL остановленного
worker, перегрузку всех узлов, потерю/возврат бэкенда, reload и очистку файлов.
